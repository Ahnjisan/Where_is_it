## 👥 기본 협업 규칙

### 1. `main` Branch 직접 작업 금지

`main` Branch에는 직접 Commit하거나 Push하지 않습니다.

모든 작업은 별도의 작업 Branch에서 진행하고, Pull Request를 통해 `main`에 병합합니다.

### 2. 작업 전 GitHub Issue 등록

기능 구현이나 수정 작업을 시작하기 전에 GitHub Issue를 등록합니다.

Issue에는 다음 내용을 작성합니다.

- 작업 목적
- 구현할 내용
- 완료 조건
- 담당자

### 3. 기능별 Branch 사용

하나의 Branch에서는 하나의 기능이나 작업만 수행합니다.

Branch 이름은 다음 규칙을 사용합니다.

```text
feature/기능명
fix/수정내용
docs/문서내용
refactor/개선내용
chore/설정내용
```

예시:

```text
feature/user-login
fix/login-validation
docs/api-specification
chore/project-setup
```

### 4. Commit 메시지 규칙

Commit 메시지는 작업 내용을 알아볼 수 있도록 구체적으로 작성합니다.

```text
feat: 새로운 기능 추가
fix: 버그 수정
docs: 문서 작성 및 수정
refactor: 기능 변경 없는 코드 개선
test: 테스트 코드 추가 및 수정
chore: 프로젝트 설정 및 기타 작업
```

예시:

```text
feat: 사용자 회원가입 API 구현
fix: 이메일 중복 검사 오류 수정
docs: 회원 API 명세 작성
chore: Spring Boot 초기 환경 설정
```

### 5. 작업 시작 전 최신 내용 반영

작업을 시작하기 전에 `main` Branch의 최신 변경 사항을 확인하고 작업 Branch에 반영합니다.

다른 팀원의 작업과 충돌할 가능성이 있다면 먼저 팀원에게 공유합니다.

### 6. Pull Request 사용

작업을 완료한 후 Pull Request를 생성합니다.

Pull Request에는 다음 내용을 작성합니다.

- 작업 목적
- 주요 변경 사항
- 테스트 및 확인 결과
- 관련 Issue
- 리뷰 시 확인이 필요한 내용

최소 한 명 이상의 팀원이 변경 내용을 확인한 후 `main`에 병합합니다.

### 7. 민감정보 Commit 금지

다음 정보는 GitHub에 Commit하지 않습니다.

- API Key
- 데이터베이스 비밀번호
- 개인 인증정보
- Access Token
- 실제 `.env` 파일
- 기타 외부에 공개되면 안 되는 정보

환경변수 이름만 `.env.example`에 작성하고, 실제 값은 팀 내부에서 별도로 공유합니다.

### 8. 작업 상황 공유

작업을 시작하거나 완료했을 때 팀원들에게 진행 상황을 공유합니다.

문제가 발생했을 경우 다음 내용을 정리하여 공유합니다.

- 발생한 문제
- 확인한 원인
- 시도한 방법
- 현재 필요한 도움

### 9. 담당 범위 외 변경 금지

자신이 담당한 기능과 관계없는 파일은 임의로 수정하지 않습니다.

공통 설정이나 다른 팀원의 담당 파일을 수정해야 한다면 먼저 팀원들과 상의합니다.
